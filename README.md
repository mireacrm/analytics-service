# Сервис аналитики

Формирует отчёты о выручке филиалов, загрузке специалистов, воронке записей
и расходе материалов.

Сервис представляет собой событийную read-модель: он получает доменные события
через RabbitMQ и формирует собственные аналитические витрины в базе
`analytics_db`. Первичные данные остаются в микросервисах-владельцах.

Для получения актуального названия филиала сервис обращается к `core-service`
по gRPC.

## Возможности

Сервис предоставляет следующие отчёты:

| Метод | Назначение |
|---|---|
| `GET /branches/{branch_id}/revenue` | Выручка филиала, количество счетов и средний чек |
| `GET /employees/{employee_id}/workload` | Загрузка и комиссия специалиста |
| `GET /branches/{branch_id}/funnel` | Воронка созданных, завершённых и отменённых записей |
| `GET /reports/consumables` | Расход материалов за указанный период |

Для отчётов период задаётся параметрами `from` и `to`.

## Доменные события

Сервис подписан на очередь `analytics-service.events` и получает весь поток
событий MireaCRM по шаблону `#`.

Основные обрабатываемые события:

- `appointment.created`;
- `appointment.completed`;
- `appointment.cancelled`;
- `invoice.issued`;
- `invoice.paid`;
- `consumables.written_off`;
- `client.registered`.

События `branch.opened`, `employee.hired` и `stock.low` регистрируются как
обработанные, но не создают отдельных аналитических витрин.

## Хранение данных

В PostgreSQL используются следующие таблицы:

- `appointment_facts` — жизненный цикл записей;
- `invoice_facts` — выставленные и оплаченные счета;
- `consumable_facts` — факты списания материалов;
- `client_facts` — регистрации клиентов;
- `processed_events` — идентификаторы обработанных событий.

Таблица `processed_events` реализует паттерн Inbox и защищает витрины от
повторного применения одного события. Отметка о событии и изменение витрины
выполняются в одной транзакции.

Время аналитического факта берётся из `occurred_at` события, а не из момента
обработки сообщения. Поэтому отчёты остаются корректными после обработки
накопившейся очереди.

## Служебные методы

| Метод | Назначение |
|---|---|
| `GET /healthz` | Проверка работы процесса |
| `GET /readyz` | Проверка готовности и доступности зависимостей |
| `GET /metrics` | Метрики Prometheus |

## Зависимости

| Пакет | Роль |
|---|---|
| [`mirea-contracts`](https://github.com/mireacrm/contracts-py) | сообщения и стабы gRPC |
| [`mireacrm-common`](https://github.com/mireacrm/py-common) | настройки, метрики, трасса, ошибки, база, события, gRPC |

Оба приезжают из своих репозиториев по версии из `pyproject.toml`.
Версию контрактов называет сервис, а не обвяз: два прямых URL одного
пакета pip считает конфликтом.

## Локально

```
pip install -e ".[dev]"
python -m pytest tests/unit -q
python -m pytest tests/integration -q   # нужен Postgres
docker build -t analytics-service .
```

Систему целиком поднимает [`mireacrm/deploy`](https://github.com/mireacrm/deploy).
